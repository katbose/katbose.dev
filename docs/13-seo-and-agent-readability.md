## 13.2 Performance practices (from the start, not retrofitted)

- **Static / ISR rendering** for all content pages — visitors almost never wait on the CMS
- **Server Components by default**; client components only where interactivity requires them
- **`next/image`** everywhere, with explicit dimensions to prevent layout shift; a custom loader
  uses Cloudflare Images for responsive transforms over immutable Supabase-CDN originals
  ([01-architecture.md](01-architecture.md) §1.4.1)
- **`next/font`** with self-hosted fonts, `font-display: swap`, and a minimal family set —
  typography is a core principle, so subset carefully rather than loading many weights
- **Minimal JavaScript** — Framer Motion used sparingly and lazily; no animation library on pages
  that do not animate
- **Route-level code splitting**; heavy features (Ask AI, syntax highlighting) load on demand
- **No layout shift** from late-loading widgets — Turnstile and analytics reserve space or load
  outside the flow
- **Cache headers** on static assets; ISR revalidation windows tuned per content type
  (posts 1h, indexes 30m)
- **Third-party budget:** PostHog, Sentry and Turnstile only. Each addition must justify its
  bytes.

### Image delivery budget

- Cloudflare Images is infrastructure, not browser JavaScript, so it does not expand the
  third-party script budget.
- Configure only 320, 640, 960, 1280 and 1920 pixel widths, `format=auto`, quality 80 and
  `fit=scale-down`; uncontrolled arbitrary widths can burn the 5,000 free unique transforms.
- Every image declares `sizes`, width/height (or a stable aspect ratio) and meaningful alt text.
- Test both paths: a transformed response from Cloudflare and the same-zone
  `onerror=redirect` fallback to the original Supabase CDN object. An image quota/error may
  increase bytes but must never produce a broken image.

## 13.3 SEO fundamentals

- Per-page `metadata`: unique title, description, canonical URL
- Open Graph and Twitter card tags on every page
- **Dynamic OG images** generated per blog post, TIE entry and project
- `sitemap.xml` generated at build from CMS content
- `rss.xml` for the blog (and optionally TIE)
- Semantic HTML with a clear heading hierarchy
- Descriptive, stable slugs — never change a published URL without a redirect
- Internal linking between related posts, projects and TIE entries
- No orphan pages: everything is reachable from navigation or an index page

**Ownership note (a gap in v1.0):** sitemap and RSS are generated by explicit route handlers in
`app/sitemap.ts` and `app/rss.xml/route.ts`, driven by CMS content — not by a build-time plugin
whose behaviour drifts from the actual content set.

## 13.4 Structured data (JSON-LD)

| Page | Schema |
| --- | --- |
| Home, Resume | `Person` — name, role, skills, social profiles |
| Blog post, TIE entry | `BlogPosting` — headline, datePublished, author, keywords |
| Project | `SoftwareSourceCode` / `CreativeWork` — name, description, codeRepository, programmingLanguage |
| All | `BreadcrumbList` |
| Home | `WebSite` with `SearchAction` pointing at Ask AI |

**`Person` identity fields:** `name: "Kat Bose"`, `email: "im@katbose.dev"`,
`telephone: "+91 9515166564"`, `sameAs: ["https://linkedin.com/in/katbose", "https://github.com/katbose"]`.

Structured data is what makes the site legible to both search engines and AI agents, which is why
it is Phase 1 work rather than a later polish item.

## 13.6 llms.txt

A curated, agent-readable index of the site — the emerging convention for making a site
consumable by language models without crawling every page.

```
# Kat Bose — katbose.dev

> Portfolio, technical blog, and engineering notes of Kat Bose.

## Pages
- [Projects](https://katbose.dev/projects): Project case studies with architecture, challenges and lessons learned
- [Experience](https://katbose.dev/experience): Professional timeline
- [Blog](https://katbose.dev/blog): Long-form technical articles
- [TIE](https://katbose.dev/tie): Short engineering notes (Things I Explore)
- [Resume](https://katbose.dev/resume): Full resume, viewable online
- [Ask AI](https://katbose.dev/ask-ai): Semantic search over all site content

## Contact
- [Contact form](https://katbose.dev/contact)
- Email: im@katbose.dev
- LinkedIn: https://linkedin.com/in/katbose
- GitHub: https://github.com/katbose
```

Keep it current when navigation changes — a stale `llms.txt` is worse than none.

## 13.9 Monitoring SEO and performance

- Lighthouse CI in the pipeline with score budgets, so regressions fail a PR rather than being
  discovered months later
- Google Search Console verified, sitemap submitted, coverage reviewed monthly
- Broken-link check as part of the dashboard's site-health widget
  ([09-observability.md](09-observability.md))
- Core Web Vitals tracked in PostHog via the Next.js `useReportWebVitals` hook, giving field data
  rather than lab data alone
