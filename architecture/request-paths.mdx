Every request to katbose.dev starts at Cloudflare's edge. Depending on the route, the request either serves a cached static response, triggers a protected form handler, or renders machine-readable portfolio content. This page traces the three primary end-to-end paths with exact references to the source files that implement them.

## Static public page

For routes like `/`, `/projects`, `/experience`, `/blog`, `/tie`, `/resume`, `/ask-ai`, and `/contact`:

```text
Visitor → Cloudflare edge → OpenNext Worker → Next.js App Router → rendered response
                                    ↓
                              R2 incremental cache
                              (NEXT_INC_CACHE_R2_BUCKET → katbose-next-inc-cache)
```

Content pages are statically rendered with ISR. A visitor request almost never blocks on the CMS. When a revalidation is needed, the Worker may fetch fresh content from `cms.katbose.dev` and update the cached response. The R2 bucket binding is declared in `apps/web/wrangler.jsonc`.

## Contact form POST /api/contact

The contact endpoint at `apps/web/app/api/contact/route.ts` is the most heavily guarded path in the application:

```text
Visitor → Cloudflare (WAF + edge rate limit)
        → OpenNext Worker → POST /api/contact
        → Turnstile siteverify (cf-connecting-ip)
        → Honeypot check (website field)
        → Rate limit (Upstash Redis, keyed by HMAC pseudonym)
        → Zod parse (ContactSchema from @katbose/shared)
        → Supabase service client insert into contact_submissions
        → after() Slack notify to #contact-form
        → JSON response {accepted: true}
```

### Step-by-step behavior

1. **Parse body**: `request.json()` is read and validated as an object. If the body is missing or not an object, return HTTP 400.
2. **Bot check**: `verifyTurnstileToken` validates the Turnstile token against the visitor's `cf-connecting-ip`. Failure returns HTTP 403.
3. **Honeypot**: If the `website` field contains any text, the request is silently accepted with `{accepted: true}` and short-circuited. This catches automated submissions without friction for legitimate users.
4. **Rate limit**: `checkContactRateLimit` in `apps/web/lib/rate-limit/contact.ts` enforces two sliding-window limits: 3 per hour and 10 per day, both keyed by the HMAC-SHA-256 pseudonym from `apps/web/lib/security/ip.ts`. If the limiter is missing credentials or times out after 2 seconds, it returns `degraded: true`, which maps to HTTP 503. A clean block returns HTTP 429.
5. **Schema validation**: `ContactSchema.safeParse` validates `name` (trimmed, 1–100 chars), `email` (valid, max 200), `message` (trimmed, 10–5000), and `website` (literal `""`). Failure returns HTTP 400.
6. **Database insert**: `createServiceClient()` from `apps/web/lib/supabase/service.ts` inserts the submission into `contact_submissions` using the service role key. If this fails, the exception is captured by Sentry and HTTP 503 is returned.
7. **Slack notification**: `after()` schedules `notifyContact` to post to `#contact-form` via the Slack webhook. Slack failure is non-blocking and captured by Sentry.

## Agent view /agent

The `/agent` route renders a canonical, machine-readable portfolio representation generated by `apps/web/lib/agent-outputs.ts`. It includes:

- Profile and experience sections
- Technology stack list
- Featured projects and latest writing
- TIE (Things I Explore) entries
- Public routes with descriptions
- Contact information

This output is designed for AI agents and assistive workflows that read the site. The `robots.txt` and `llms.txt` files are also generated from the same typed route manifest in `apps/web/lib/routes.ts`.

<Note>
  AI Search and resume signed-URL paths (Phases 3–4) are planned and gated by their respective spikes. They are not yet implemented in the repository.
</Note>
